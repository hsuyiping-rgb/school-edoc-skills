# 招標文件審查（上網公告前）

## 這個技能在做什麼

機關承辦人把一疊招標文件送出去公告之前，需要有人用採購法的眼光把它讀一遍。這件事的價值不在於「挑錯字」，而在於**攔截三種會讓案子翻掉的問題**：

1. **違法** — 等標期不足、金額級距與招標方式不符、限制競爭條款。廠商一提異議就要重來，還可能被採購稽核小組記缺失。
2. **綁標之虞** — 需求說明書寫進特定廠商的型錄品名，或機關把規劃內容都填好了。這種案子事後最難辯解。
3. **文件不完備** — 範本套錯、「由機關於招標時載明」的欄位留白、規格寫不出來。這些不會馬上出事，但決標後、驗收時全部變成爭議。

審查的產出是給承辦人和主管看的，所以要具體到「哪一份文件、第幾條、改成什麼」，而不是泛論。

## 工作流程

### 步驟 1：把文件讀出來

招標文件通常是 `.doc`／`.docx`／`.pdf` 混雜，而且公文 PDF 常是 Big5 CID 編碼，直接讀會變亂碼。用內附腳本一次轉成純文字：

```bash
python scripts/extract_docs.py <招標文件資料夾> -o <輸出資料夾>
```

腳本會處理 `.docx`（含表格）、`.doc`（Windows 走 Word COM，其他平台走 LibreOffice）、`.pdf`（PyMuPDF）、`.xlsx/.ods`。輸出為 UTF-8 純文字，檔名對應原檔。

**一定要把估價單的表格內容讀出來**——多數問題都藏在那裡。

典型的一套文件包含：簽呈、投標須知、契約、投標聲明書、標單、需求說明書及估價單、監辦通知單。缺哪一份也要記下來，本身就是發現。

### 步驟 2：先抓四個定錨數字

在讀細節之前，先把這四項找出來，因為後面每一條檢核都依賴它們：

| 項目 | 去哪裡找 | 為什麼重要 |
|---|---|---|
| 預算金額 | 簽呈、投標須知重要條款 | 決定金額級距 |
| 金額級距 | 與公告金額（目前 150 萬）比對 | 決定招標方式、等標期、監辦方式是否合法 |
| 招標方式與決標原則 | 投標須知重要條款 | 決定適用哪一套程序規定 |
| 公告日與截止投標日／時 | 簽呈時程、投標須知、外標封 | 等標期計算的輸入值 |

### 步驟 3：跑檢核清單

讀 `references/checklist.md`。那份清單按文件別組織（簽呈／投標須知／契約／需求說明書及估價單／標單／監辦通知單／跨文件一致性），每一條都寫了要看什麼、依據是什麼、常見的錯法長什麼樣。

清單很長，但不必機械式逐條套。**先掃過整份清單建立地圖，再針對這個案子實際有的東西深入查。**

有四個地方特別容易出事，值得每次都認真算一次：

**等標期** — 最常違法、也最容易算錯的一項。`招標期限標準 §11` 規定公告當日算入，但截止收件日「以當日下班時間為截止時間者，始算一日；未達下班時間者，該日不算入」。所以截止時間訂 17:00 而機關下班時間是 17:30 的話，那一天不算，等標期直接少一天。這個陷阱很隱蔽，要主動問承辦人機關的下班時間，不要自己假設。

**採購性質（工程／財物／勞務）** — 學校和小型機關最常誤判。看估價單有沒有拆除、油漆、門窗更換、牆面裝修、管線這類項目；有的話就不是單純「購買」。`採購法 §7 IV` 規定兼有性質者依預算金額比率最高者歸屬，但如果估價單的單價欄全部留白給廠商填，機關其實無從判斷比率——這本身就是一個發現。判斷結果會連動影響契約範本、廠商資格（是否需營造業或室內裝修業登記）、勞安責任。

**綁標訊號** — 需求說明書或估價單裡出現具體到不像通用描述的品名（帶型號、套組代號、系列件數），八成是抄某家廠商的型錄。另一個訊號是機關把「規劃內容」「設計理念」欄位自己填好了——那正是要交給廠商在企劃書裡競爭的東西，先填好等於評選只是走過場。

**空白欄位** — 契約與投標須知的範本裡有大量「由機關於招標時載明」「未填時為⋯」的欄位。這些留白不會讓文件看起來有問題，但每一個都是決標後的爭議來源。用關鍵字掃過去：

```bash
grep -n "由機關於招標時載明\|由機關載明\|未填時\|未載明者\|未勾選者" <轉出的文字檔>
```

保險金額下限、保固保證金比率、合格分數、釋疑期限、減價收受比率，都是這樣漏掉的。

### 步驟 4：分級

每個發現歸到四級之一。分級不是形容詞，是在回答「承辦人現在該做什麼」：

- **重大** — 上網前必須處理。違法，或有被提異議、被認定綁標的具體風險。
- **應補正** — 文件欄位未完成、範本套錯、揭露不足。不改也能上網，但一定會在後段出事。
- **建議** — 不違法，但影響競爭、履約品質或安全。
- **已符合** — 明確查過沒問題的，也要列出來。這讓報告可信，也讓主管知道哪些不用再看。

一個案子如果通篇都是「重大」，通常是分級太寬鬆了；反過來，如果連等標期不足都歸在「建議」，報告就失去意義。

### 步驟 5：引用法條時保持誠實

這一步很重要，因為**寫錯的條號會被承辦人原封不動抄進招標文件，變成一個新的瑕疵**。

讀 `references/legal-basis.md`，那裡有常用法條與標準的對照表，以及哪些項目風險高、必須查證。原則是：

- 採購法本文與施行細則的條號可以憑記憶引用，但涉及日數、比率、金額的具體規定要查原文（全國法規資料庫）。
- **CNS 國家標準編號一律標示為待查。** 板材甲醛分級、塗料、鋁窗氣密性這些標準的編號很容易記混，寫錯就是害人。如果不確定，改以文字描述（「甲醛釋出量達 F☆☆☆ 級以上」）而不寫編號。
- 子法（各種辦法、標準）的條號如果沒查過，在報告裡寫法規名稱即可，不要硬掰條次。
- 報告末尾的免責段落要說清楚審查範圍（只看書面、沒有現場勘查、沒有市場行情查證）。

### 步驟 6：產出 Word 文件

寫一個 JSON 資料檔，然後用內附腳本產生 Word：

```bash
node scripts/build_report.js <資料.json> <輸出.docx>
```

JSON 格式與可用的行內標記（`**粗體**`、`` `法條` ``）詳見 `references/report-format.md`。腳本會處理版面、配色、表格、分頁，不需要自己寫 docx-js。

`assets/example-review.json` 與 `assets/example-spec.json` 是兩份完整的範例，照著改比從頭寫快。

**產出兩份文件：**

1. **審查報告** — 主要交付物。四級發現、時程檢核表、已符合清單、建議處理順序。
2. **規格補正建議表** — 只要估價單有品項缺規格就要出。這份是可以直接貼進需求說明書的規格稿，不是再一次的問題清單。撰寫方式與常見品項的規格範式見 `references/spec-patterns.md`。

檔名建議用 `<案號>-招標文件審查報告.docx`、`<案號>-採購品項規格補正建議表.docx`，存在招標文件同一個資料夾。

### 步驟 7：檢查排版

Word 產出後要真的看一眼，不要假設它是對的：

```bash
python scripts/render_check.py <輸出.docx> -o <暫存資料夾>
```

會轉成 PDF 並輸出每頁 PNG。讀那些圖，確認表格沒破版、方塊沒被硬切在頁面中間、中文字型正確。

## 給承辦人的話怎麼寫

報告是給非法律背景的總務主任和校長看的。幾個原則：

- 每個發現都要能回答「所以我現在要改什麼」。只說「不符 §26」沒有用，要說「刪除第 15 項的『X 套組』，改寫成：壁掛式操作板，含轉盤、齒輪、滑軌等操作元件 ___ 種以上」。
- 承辦人做不到的事要標出來。有些規格必須現場丈量、有些數量要問治療師或教師，這些列成「須先行確認事項」，不要假裝可以憑空填。
- 如果建議的作法會讓案子延期，直說。時程是承辦人最在意的事，含糊帶過反而不負責任。
- 有更省事的合法替代方案就提。例如全案只買一台筆電，改走共同供應契約（`採購法 §93`）另案訂購，比在標案裡寫規格更省事，還順便迴避原產地限制的問題。
